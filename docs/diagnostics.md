# Диагностика iTime: как мы перестали кормить гуру перезагрузками

Это **фактический журнал эксперимента пользователя**, а не синтетический бенчмарк.

## Симптом 1: LCD включён, но только квадратики

Первая строка заполнена прямоугольниками, вторая пустая. Исправлено первоначальной прошивкой **LiquidCrystal**: обе строки показали **hello esp32! / lcd 1602 ready**. Значит, сам параллельный LCD и его 4-битное управление работали.

## Симптом 2: вместо часов — reboot loop

После добавления Wi-Fi/NTP устройство показывало «wifi connecting» и перезапускалось с сообщениями:

~~~text
Guru Meditation Error: Core 1 panic'ed (LoadStoreAlignment)
Guru Meditation Error: Core 1 panic'ed (IllegalInstruction)
rst:0xc (SW_CPU_RESET)
~~~

Для диагностики был составлен **Wi-Fi-only** скетч без LCD и NTP. Он выводил:

~~~text
boot ok
~~~

и далее снова:

~~~text
Guru Meditation Error: Core 0 panic'ed (IllegalInstruction)
~~~

Повторялось **даже после полного отсоединения дисплея**. Это исключило код управления LCD из непосредственной цепочки падения, но не доказывало неисправность Wi-Fi-чипа.

## Симптом 3: нестабильная загрузка инструкций при 80 МГц Flash

В аварийных логах наблюдали:

~~~text
mode:DIO, clock div:1
Guru Meditation Error: Core 0 panic'ed (IllegalInstruction)
~~~

В нескольких сбоях менялись байты в дампе инструкций по одному адресу. Это **совместимо с проблемами чтения флеш-памяти**, но не является самостоятельным доказательством конкретной аппаратной неисправности.

## Рабочий обход

Скомпилировали и загрузили Wi-Fi-only тест с настройками:

~~~powershell
arduino-cli compile --clean --fqbn "esp32:esp32:esp32:FlashFreq=40,FlashMode=dio" .
arduino-cli upload -p com3 --fqbn "esp32:esp32:esp32:FlashFreq=40,FlashMode=dio" .
~~~

Новый boot log:

~~~text
mode:DIO, clock div:2
boot ok
wifi mode ok
wifi begin called
uptime: 6
wifi status: 3
ip: 192.168.10.21
signal: -82
uptime: 14
wifi status: 3
ip: 192.168.10.21
signal: -83
~~~

Фактический результат: программа пережила предыдущую точку сбоя, получила DHCP-адрес и успешно подключилась к сети. После возвращения LCD на фото **отображались дата и время**.

## Что именно значит 40 МГц

**FlashFreq=40** — частота SPI Flash, из которой процессор читает код. Это **не** частота CPU, **не** скорость Wi-Fi, **не** скорость порта COM и **не** частота обновления LCD.

- **clock div:1** в этой конфигурации отражал Flash 80 МГц.
- **clock div:2** — Flash 40 МГц.

**FlashMode=dio** — двухлинейный режим обмена с внешней SPI Flash.

В документации не стоит объявлять ошибку «вылеченной навсегда»: нужны тест питания 3,3 В под нагрузкой, проверка USB-кабеля, длительный Wi-Fi soak test, декодирование Backtrace по ELF и, при необходимости, проверка флеш-памяти.

## Что делать, если на другой машине опять Guru Meditation

1. Отсоединить LCD при выключенном питании; проверить Wi-Fi-only программу.
2. Проверить **arduino-cli core list** и установленное ядро.
3. Пересобрать с **FlashFreq=40,FlashMode=dio**, чистой сборкой.
4. Проверить boot log **mode:DIO, clock div:2**.
5. Проверить питание/USB-кабель, сигнальные соединения.
6. Если проблемы останутся — декодировать Backtrace по ELF. Без ELF нельзя надёжно назвать падающую функцию.

## Слабый сигнал Wi-Fi

Измеренное значение **−82…−83 dBm** — слабый уровень. Работало в тесте, но для ежедневной эксплуатации лучше улучшить приём. DHCP-адрес **192.168.10.21** относится к конкретному запуску, другим устройствам этот IP не обещан.

## Полезные команды

~~~powershell
arduino-cli version
arduino-cli board list
arduino-cli core list
arduino-cli monitor -p com3 --config baudrate=115200
~~~

> «Сборка прошла успешно» не значит «плата стабильна». Это значит только, что компилятор ещё не видел твоих проводов.
